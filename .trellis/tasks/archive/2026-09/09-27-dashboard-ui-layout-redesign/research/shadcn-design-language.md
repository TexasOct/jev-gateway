# shadcn/ui design-language research

Research only. This compares the current working tree with the official shadcn/ui theming scaffold and the `new-york-v4` registry source. No product files, dependencies, or live gateway state were changed. The registry source and documentation are moving targets; the linked pages should be checked again when implementation begins.

## What "original shadcn/ui" means here

shadcn/ui supplies semantic theme tokens and source-owned component implementations, not one immutable product theme. Its [theming guide](https://ui.shadcn.com/docs/theming) calls the listed `neutral` colors a *default scaffold* to copy and adjust. In that scaffold, light `background`/`card` are white, `foreground` is near-black, `secondary`/`muted`/`accent` are quiet neutral surfaces, and `primary` is near-black. Dark mode reverses the near-black and near-white foundation. The scaffold sets `--radius: 0.625rem`, with `@theme inline` radius aliases (`rounded-md` derives from `--radius-md: calc(var(--radius) * 0.8)`, `rounded-lg` from `--radius-lg: var(--radius)`, and `rounded-xl` from `--radius-xl: calc(var(--radius) * 1.4)`). Its dark selector uses `.dark`; JEV already has a different, intentional scheme selector.

The scaffold's shadcn `accent` is a subtle hover/selection *surface*, distinct from its filled `primary` action. It also declares paired foreground roles, `popover`, `input`, `ring`, destructive, chart, and sidebar tokens. Exact neutral scaffold examples include light `--primary: oklch(0.205 0 0)`, `--secondary: oklch(0.97 0 0)`, `--border: oklch(0.922 0 0)` and dark `--background: oklch(0.145 0 0)`, `--card: oklch(0.205 0 0)`, `--accent: oklch(0.269 0 0)`. These are reference values, not values JEV can paste in without replacing its dynamic seed contract.

The [official Button documentation](https://ui.shadcn.com/docs/components/radix/button) lists `default`, `outline`, `ghost`, `destructive`, `secondary`, and `link`, with sizes `default`, `xs`, `sm`, `lg`, `icon`, `icon-xs`, `icon-sm`, and `icon-lg`. The inspected [`new-york-v4` Button source](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/new-york-v4/ui/button.tsx) uses `rounded-md text-sm font-medium`, a 3px half-opacity focus ring, default `h-9`, small `h-8`, large `h-10`, icon `size-9`, low shadow on outline, and `disabled:opacity-50`. Its filled destructive variant uses destructive background and white foreground. These are registry-source styles, not universal accessibility sizes; JEV's 36px ordinary and 40px canvas control minimums remain project requirements.

The inspected [`new-york-v4` Card source](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/new-york-v4/ui/card.tsx) uses `gap-6 rounded-xl border bg-card py-6 text-card-foreground shadow-sm`, with `px-6` sections, `font-semibold` title and `text-sm text-muted-foreground` description. `CardTitle` is a `div`, so callers supply a semantic heading. The [current Card docs](https://ui.shadcn.com/docs/components/radix/card) additionally describe `size="sm"` and `--card-spacing`; the inspected `new-york-v4` file does not have that prop. Treat the docs and that particular registry snapshot as different revisions, and pin the intended component source at implementation time rather than mixing their APIs.

There is no single required dashboard type scale in the theme scaffold. The current [typography page](https://ui.shadcn.com/docs/components/typography) describes an optional `shadcn/typeset` CSS file for prose/Markdown, with body font inherited and adjustable heading/mono fonts. It does not impose a global dashboard font. The clean `text-sm font-medium` control rhythm, restrained muted descriptions and tighter heading tracking are useful references; adopting a new remote font or prose stylesheet is unnecessary.

## User decision

The user explicitly asked to align the frontend more closely with the original shadcn/ui visual language. Treat New York's neutral surfaces, typography, radii and component density as the visual target, not merely as source material for a few primitives. Keep the existing dynamic JEV palette contract unless the user separately approves replacing the seed-derived primary.

## Current JEV baseline and divergences

- `frontend/package.json` already has Tailwind v4, its Vite plugin, CVA, Radix Slot/Separator, `clsx`, and `tailwind-merge`; `frontend/vite.config.ts` retains `/dashboard/` and the bundled static output. There is no `frontend/components.json`, so existing `src/ui/` files are project-owned adaptations, not a CLI-managed shadcn installation.
- `frontend/src/tailwind.css` imports theme and utilities without Preflight, retains native-control base rules, and maps semantic colors to the runtime palette. `@custom-variant dark` targets `[data-scheme="dark"]`. `--color-primary` maps to JEV `--accent`, whereas `--color-accent` maps to the subdued `--surface-alt`. This distinction is correct and should remain explicit.
- `frontend/src/theme/palette.ts` derives both palettes from one saved seed and applies `--bg`, `--surface`, `--surface-alt`, `--border`, `--text`, `--accent`, its hover/active/on-accent variants and status roles as root inline variables. It enforces contrast targets of 4.5 for body/foreground pairs and 3 for status colors. `frontend/src/styles.css` provides fallback token values and a system-font body at 14px/1.5. Its current blue-tinted background and surfaces, border colors, and blue filled navigation make the app visually different from the neutral shadcn scaffold.
- `frontend/src/ui/button-variants.ts` borrows the `new-york-v4` variant structure but uses 13px text, a 2px outline rather than the registry's 3px ring, 36px small controls, 40px icons, explicit borders on all variants, and an outlined destructive button. `frontend/src/ui/button.tsx` uses Slot and defaults native buttons to `type="button"`, a useful form-safety adaptation. `frontend/src/ui/card.tsx` uses an 8px radius, 16px spacing, no shadow, and smaller title/description text than the cited registry Card. `Separator` is close to the Radix-backed registry pattern.
- `frontend/src/App.tsx` uses a blue filled segmented active tab, rounded-xl header navigation and a mix of raw buttons and owned `ToolButton`/`Button`. `MonitoringView.tsx` and `AppearanceView.tsx` use owned Cards but override padding. The canvas has bespoke node shapes and measured overlays in `styles.css`; those are graph affordances, not generic shadcn cards.

## Proposed mapping for the next design pass

| shadcn role or cue | JEV mapping | Proposed treatment |
| --- | --- | --- |
| `background`, `foreground` | `--bg`, `--text` | Preserve seed application, but lower surface hue/saturation in `palette.ts` so the page reads as a neutral base. Re-run measured contrast for every permitted seed. |
| `card`, `card-foreground`, `popover`, `popover-foreground` | `--surface`, `--text` | Add explicit popover aliases only when a real overlay uses them. Keep panel/card surfaces quieter than selected actions. |
| `secondary`, `muted`, `accent` plus paired foreground roles | `--surface-alt`, `--text` / `--text-muted` | Keep shadcn `accent` as the subtle hover surface; never map it to actionable JEV `--accent`. Ensure muted text still clears the existing contrast contract. |
| `primary`, `primary-foreground`, `ring` | `--accent`, `--on-accent`, `--accent` | Keep seed-derived blue/color primary for saved theme behavior. Use it sparingly for primary actions and selected path; use a subtle selected tab with foreground text if seeking the neutral shadcn look. Exact neutral black primary would be a separate product decision because it alters seed meaning. |
| `destructive`, `border`, `input` | `--bad`, `--border`, `--border` | Preserve semantic danger and the existing action safety gates. Check borders/controls in both schemes; adding separate input or destructive foreground roles needs contrast verification. |
| `--radius` and aliases | currently assorted hard-coded radii | Consider one radius scale using the scaffold's `0.625rem` reference, while keeping geometry-dependent node/inspector exceptions. Radius change is a project adaptation, not proof the current registry will ship those values forever. |
| Button/Card source styles | `src/ui/button-variants.ts`, `src/ui/card.tsx` | Move normal buttons toward `text-sm`, consistent focus ring, restrained outline/ghost states, and cards toward `rounded-xl`, `gap-6`, `px-6` where space allows. Keep minimum touch size, semantic headings, and compact variants for dense lists; avoid blindly adding Card shadows to every nested monitoring panel. |

A restrained first pass could neutralize palette surfaces and borders, unify body/control typography around 14px, reduce saturated active-navigation fill, and align ordinary Cards/Buttons. It should leave the strategy diagram's semantic edge colors and selected/focused states legible. If exact shadcn `neutral` light/dark palettes and black/white primary are desired instead of a seed-derived interpretation, obtain an explicit decision on appearance seed behavior before changing palette code.

## Preserve and verify

Keep the Tailwind Vite bundle and no-Preflight migration until the native-control reset and canvas rules can be replaced safely. Do not scaffold shadcn over `styles.css` or let the default `.dark` selector override `data-scheme`. Preserve `/dashboard/` assets/CSP, both locales, memory-only credentials, the single saved theme seed, and no additional browser persistence. Keep the 100dvh strategy shell, `190 x 56` node hit regions, ports, measured `[data-canvas-occlusion]` toolbar/inspector/drawer bounds, virtual list fixed row/window dimensions, and the independent layout versus policy write paths. Typography, border, or padding changes on overlays and nodes require browser pointer/Fit/occlusion checks even if snapshots look good.

Validation for a later implementation: compare desktop, tall, 390px and 320px in EN/ZH and both schemes; inspect computed colors and contrast for varied seeds; keyboard focus/disclosures and canvas hit targets; virtual-list scrolling; reduced-motion route explanation; no document overflow; asset build and CSP/security tests. No such implementation or browser validation was performed for this research note.
