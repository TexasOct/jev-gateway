# Dashboard interaction analysis (read-only)

## Scope and evidence

This is a source-level assessment of the current working tree, not a browser usability test. I read this task's `prd.md`, `design.md`, and `research/design-language.md`; the prior visual-language `research/style-spec.md` and `research/ui-audit.md`; and `frontend/src/App.tsx`, `frontend/src/monitoring/{MonitoringView,VirtualList,RouteTrace}.tsx`, `frontend/src/config/RoutingEditor.tsx`, and the relevant monitoring CSS. No product source was changed, no follow-up task was created, and no real gateway data was queried. Benefits below are hypotheses to validate with synthetic fixtures. Prior audit screenshots used empty monitoring data, so they cannot establish populated-list usability.

The redesign already provides a gateway-activity overview, an explicit latest-session preview action, a selected-session summary, retained-evidence disclosures, a collapsed provider table, virtual lists, and route playback. The recommendations below build on those features rather than treating them as absent. Preserve the PRD's distinction between recorded outcomes and live state, and the editor's validate → review → warning acknowledgement → explicit apply flow.

## Pure presentation refinements within the existing interaction contract

These do not require changing selection, data fetches, persistence, keyboard commands, pagination, or replay behavior. They still need visual and accessibility review.

| Priority | Opportunity and source evidence | Expected benefit | Risk / compatibility | Testable acceptance criterion |
| --- | --- | --- | --- | --- |
| P1 | Make the overview's timestamp and result explicitly read as the **latest recorded request**, and distinguish the unselected preview from a selected session. `SessionOverview` shows a timestamp and status without a result label; the preview draws from `sessions.data[0]` while `selectedSessionId` remains null (`MonitoringView.tsx:131-153,157-185`). | A newcomer can tell what is recorded and what action selects a session without interpreting the timestamp as live health. | Copy must be localized in both languages and must not call an unknown outcome “pending” or guarantee recency beyond the list's contract. Keep the preview non-selected until its button is pressed. | With fixture states for success, failure, unknown and no latest request, both locales name the recorded result or its absence; `aria-pressed` remains false until selection; no new network request occurs merely from rendering the preview. |
| P1 | Make selected-request affordance and the two evidence levels easier to scan: the request header selects the inline trace; trace-stage and raw JSON `<details>` can be opened independently (`MonitoringView.tsx:86-107`; `RouteTrace.tsx:270-307`). A short localized hint or clearer headings can explain this without exposing raw payloads by default. | First-time users can find the route and outcome; experts can locate the full retained JSON without guessing which disclosure contains it. | Keep native `<details>`, keyboard reachability, bounded card scrolling, and wording that says “recorded” or “available” rather than “live.” Avoid taller fixed virtual rows; long evidence must scroll inside the 360px card. | At 320px and desktop widths, keyboard-only users can select a request, inspect each stage, then open all four raw JSON sections; no clipping or document-level horizontal overflow occurs. |
| P2 | Clarify the provider panel's role beside the disclosure. The caveat is already outside the collapsed `<details>`, while the table labels and values become visible only after expansion (`MonitoringView.tsx:237-262`). Keep the caveat adjacent and make the disclosure's scope (“retained observations,” not health) clear. | Reduces the chance that historical attempts are read as live provider health. | Do not synthesize health summaries, reorder evidence columns, or suppress failures; preserve `td[data-label]` mobile semantics and contained table overflow. | In both schemes and locales, before and after expansion, a reader sees the retained-evidence caveat; all recorded columns and unavailable markers remain reachable by keyboard and on narrow screens. |
| P2 | Keep the strategy drawer's current collapsed default, but strengthen the visual distinction among overview, advanced editors, saved pool order, and pending changes. The drawer has four native disclosures and a separate action toolbar (`RoutingEditor.tsx:578-770`; `research/strategy-presentation-audit.md`). | Experts can find the right editor or review surface faster without weakening the policy safety gate. | Presentation only: do not move the action toolbar, resize measured overlays, change the DnD hit boxes, or replace disclosure semantics. | Keyboard navigation reaches each disclosure and review action in both locales at 320px and desktop; opening the drawer leaves canvas controls usable and does not change payloads or editor state transitions. |

## Behavior changes requiring explicit product approval

These extend or alter contracts frozen by this redesign's PRD/design. Treat them as separate decisions, not as authorized implementation work.

| Priority | Opportunity and source evidence | Expected benefit | Risk / compatibility | Testable acceptance criterion if approved |
| --- | --- | --- | --- | --- |
| P1 | Give session-detail loading its own visible state and prevent misleading “no session selected” messaging. `selectSession` clears `detail` and starts an async request (`App.tsx:233-255`), but the request-panel metadata chooses `t("noSessionSelected")` whenever `detail === null` and there is no error (`MonitoringView.tsx:216-220`), even with a selected session. The overview separately says records are loading. | Removes contradictory feedback while users switch sessions, especially on a slow connection. | Requires passing/deriving an explicit initial-detail loading state or refining render logic. Preserve abort/generation guards and distinguish missing retained evidence from loading. | With delayed synthetic detail responses, the selected session remains identified; the request panel says it is loading, never “no session selected”; stale responses cannot replace a newer selection, and failures offer retry. |
| P1 | Make refresh scope and progress explicit. The header has one `Refresh` action, and `refresh` clears selected request/detail and reloads sessions, selected detail, configuration and theme (`App.tsx:198-224,376-382`). It can interrupt a request inspection, and the label does not tell the user its broad scope. | Experts can update the data they intend to inspect without losing their place unexpectedly. | Any scoped-refresh design changes request sequencing and may affect unsaved appearance/strategy drafts; do not promise preservation until concurrent refresh, auth and config-hash remount behavior is specified. The safer first decision may simply be explicit copy/progress for the existing global refresh. | With an expanded request disclosure and a selected request, fixture-triggered refresh shows a busy/error state; selection/focus/scroll preservation or reset follows the approved rule; no stale response wins; theme/config reads are counted as specified. |
| P2 | Offer a discoverable manual path for more pages. `VirtualList` loads additional pages when scrolling approaches the end and renders no ordinary “load more” button while `hasMore` is true; only a failed page adds a retry button (`VirtualList.tsx:44-46`; `MonitoringView.tsx:192-231`). | Helps keyboard users and users who do not infer infinite scrolling; gives advanced users more control over when evidence is fetched. | Changes pagination UI/trigger and potentially request volume. Keep cursor deduplication, busy guards, virtualized focus retention and separate session/request page errors. | Synthetic multi-page lists can be fully traversed by keyboard and pointer, either through the agreed manual action or scroll; each cursor is fetched once per active generation; failed pages preserve earlier rows and expose retry. |
| P2 | Preserve orientation when changing views or reloading configuration. `openView("strategy")` fetches configuration and `RoutingEditor` is keyed by `config_hash` (`App.tsx:281-289,450-455`); a changed hash can remount the editor. Drafts, inspector selection and drawer state live inside the editor (`RoutingEditor.tsx:289-305,470-526`). | Prevents advanced users from losing work context without warning when server configuration changes. | A draft-preservation policy needs conflict handling and cannot quietly apply stale changes. Authentication is memory-only; do not add storage without approval. | With an unsaved draft, a synthetic configuration-hash change produces the approved discard/keep/review decision; no stale draft is applied without validation, warning acknowledgement and explicit confirmation. |
| P3 | Decide whether the first unselected preview should be selected automatically or remain explicit. Current behavior previews `sessions.data[0]`, and the user must press “Select this session” or a row before detail loads (`MonitoringView.tsx:157-185`; `App.tsx:233-255`). | Auto-selection could shorten the first-use path, but the current explicit choice makes additional evidence fetches intentional. | Changes initial API traffic, focus/scroll behavior and the distinction between preview and selection. The present explicit action already satisfies the design direction; only change after observed usability evidence. | If approved, initial load selects exactly the intended session once, explains why it was selected and keeps keyboard focus predictable; if not approved, the preview remains unmistakably unselected and requires no detail fetch. |

## Recommended decision order and validation

Start with the P1 presentation labels and the selected-detail loading-state discrepancy. Next, ask whether refresh should remain global or become scoped before changing its handler. Evaluate manual pagination with keyboard-only synthetic fixtures, then decide on configuration-conflict handling. Do not bundle auto-selection with these fixes: it adds requests and changes the first-use contract without evidence that the existing preview action fails.

Use synthetic delayed/failed/empty/paginated data and long route/model names in both locales, light/dark schemes, and desktop/390px/320px viewports. Verify focus, disclosure reachability, request abort ordering, and the editor's unchanged review/apply safety gate. The earlier UI audit notes that empty-monitoring screenshots do not test populated pagination; passing pure-function tests likewise does not establish real scroll/focus behavior. This document makes no claim that any proposal has passed a browser test.
