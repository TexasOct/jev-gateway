# Decisions needed before implementation

The release task is still planning; its PRD has TBD requirements and acceptance criteria (`.trellis/tasks/09-24-release-latest-curl-publishing/prd.md`). Settle these before a design or publication workflow is approved.

1. **What is the install artifact?** Choose the release wheel, an sdist, or Git source pinned to the latest published release tag. The wheel already builds as `py3-none-any` (`pyproject.toml:7,25-31`; local `dist/` inspection), while the existing installer uses `uv tool install --force git+...@main` (`scripts/install.sh:48-55`). A release tag lookup followed by git installation would pin source code, but would not install the published wheel. Decide whether publishing the wheel is part of the installer contract or a separate deliverable. Name the asset and package version rules explicitly.
2. **Where should the one-line curl command fetch the bootstrap?** Raw `main` in both READMEs and docs remains mutable even when it installs a release artifact. Options include a release asset at `/releases/latest/download/install.sh` or a stable raw bootstrap that resolves a release tag. The former couples initial bootstrap availability to the first release; the latter leaves the bootstrap on `main`. Decide the desired integrity and first-release behavior.
3. **What do `--ref` and `JEV_INSTALL_REF` mean after the switch?** Preserve a way to pin a version, allow arbitrary git refs as an explicit developer escape hatch, replace the flag with `--version`, or support both with unambiguous precedence. Today all refs map to git URLs and state says `method: isolated`, `ref: main`, `source: git+...@main` (`scripts/install.sh:4-12,48-58`; `jev_gateway/cli/install_state.py:16-23,43-59`). Define provenance fields for asset installs and how `--dry-run` reports a latest release without silently performing a network lookup.
4. **What happens if latest is unavailable?** The live release list is empty and `releases/latest` returns 404. Decide whether the installer fails with a clear actionable error or explicitly falls back to `main`. A silent fallback would undermine the release-only promise. Also decide whether prereleases can be requested explicitly; GitHub's latest-release API excludes drafts and prereleases ([API reference](https://docs.github.com/en/rest/releases/releases)).
5. **How are releases authorized and published?** Choose tag-driven automated publication, manually approved `workflow_dispatch`, or manual GitHub release creation plus an upload workflow. Define version/tag shape (for example `v0.1.0`), release notes, whether a first release is published now, and how a bad release is replaced or rolled back. A tag push and a GitHub Release are separate objects. If one workflow's `GITHUB_TOKEN` creates a release, do not depend on that event launching a second workflow ([GitHub token trigger rules](https://docs.github.com/en/actions/concepts/security/github_token)).
6. **What verification is mandatory?** Select a checksum/signature or attestation policy, whether to test the published asset on both macOS and Linux, and whether only a tested release is marked latest. At minimum, enforce version consistency and wheel contents, test a clean installation, and keep publisher permissions narrow. The current installer verifies no package digest (`scripts/install.sh:48-55`); `.trellis/spec/backend/quality-guidelines.md` requires wheel metadata/license and frontend freshness checks before packaging.
7. **What is explicitly outside this release?** The preceding curl task excludes Homebrew tap publication and Windows installation (`.trellis/tasks/09-24-curl-install-and-cli/prd.md`, Out of scope). Confirm whether PyPI, containers, Homebrew, self-update, and private-release authentication remain out of scope so the public release workflow has a finite acceptance test.
