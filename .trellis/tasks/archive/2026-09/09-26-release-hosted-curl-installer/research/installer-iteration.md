# Installer iteration: tests, CLI provenance, and installation docs

## Existing compatibility contracts

- `tests/test_install_script.py:12-25` requires `--dry-run --no-init --home` to avoid network and `uv` execution while describing latest stable, the unverified dry-run, and a verified wheel install. `:136-154` requires `--no-uv` dry-run to fail without bootstrap, release lookup to fail before `uv` bootstrap, and `--ref`/`--version` exclusion to return status 2. Preserve the non-mutating dry-run even if another release's installer would normally be fetched for `--version`: describe the handoff rather than downloading and invoking it during dry-run.
- The offline fixture at `tests/test_install_script.py:28-68` executes the local `scripts/install.sh` with a fake GitHub API, wheel, checksum, `uv`, and `jev`. Its fake `jev` only records argv, so `:71-77` proves ordering and the CLI provenance handoff, not a persisted install state. Fixture changes will be needed to model `install.sh` and `install.sh.sha256`, calls to both latest and tagged URLs, and verification before any child shell invocation. Keep `--yes`, `--home`, `--no-init`, `--no-uv`, optional leading `v`, explicit prereleases, and validated `--ref` behavior (`:80-83`, `:128-154`; `scripts/install.sh:9-40`).
- Failure tests cover missing wheel/checksum, bad wheel digest, missing or malformed release metadata, malformed checksum lines, and wrong asset origin (`tests/test_install_script.py:86-125`). They do not cover a missing installer or its sidecar, bad installer digest, selected-tag mismatch, a redirected `latest` selection changing between asset requests, `--version` re-execution, or forwarded flags. Add a fake child installer that records invocation and assert it never runs on installer verification failure; assert `uv` never runs on wheel failure. The existing fixture's broad `*sha256` branch would return the wheel checksum for an installer sidecar until split by asset name.
- Release validation tests build a real wheel, check exact sidecar contents, and corrupt one packaged Python file (`tests/test_release_validation.py:37-58`). Add validation cases for the standalone installer's generated release identity, exact `install.sh.sha256` filename/digest format, missing or altered installer, and absence of extra publishable artifacts. Existing `scripts/validate-release.py:15-27` checks `v<pyproject version>` and one wheel, and `:65-67` creates only the wheel sidecar. Testing the publishing manifest separately matters: passing validator output alone does not prove the workflow uploads the two installer assets.
- `jev install init --version V --source URL` accepts a normalized version without `v` and precisely `https://github.com/TexasOct/jev-gateway/releases/download/vV/jev_gateway-V-py3-none-any.whl`; it rejects `--ref` and any other source (`jev_gateway/cli/main.py:235-244`). It does not independently verify either asset, or prove that the installed distribution matches the caller-supplied version. The script must pass the verified wheel's exact tagged URL and resolved version. Provenance should continue describing the wheel, not the installer URL. `tests/test_cli_main.py:25-44` covers a valid prerelease and an invalid version/source; add a syntactically valid version with a mismatched but GitHub-looking URL, `--source` without `--version`, and combined `--ref` rejection as useful CLI regressions.
- `jev_gateway/cli/install_state.py:21-34,41-69` stores `package_version`, `source_type: release_wheel`, exact `source`, and blank `ref` for release installs. Existing state preservation and legacy Git reading are tested in `tests/test_cli_install_state.py:16-42`. The test directly invokes `init_runtime`, so it does not prove the release-hosted installer actually writes that state; a disposable-home integration test can bridge this with a real CLI entry point. Uninstall should still retain runtime data by default (`tests/test_cli_install_state.py:7-13`).

## Documentation anchors

- `docs/cli.md:7-15` and `docs/local-install.md:20-32` still instruct readers to execute raw `main` and call it the bootstrap. Replace those URLs and descriptions with the latest release asset and pinned `vX.Y.Z` examples. Distinguish initial latest selection, explicit prerelease/rollback via pinned URL or `--version`, and the separate `--ref` developer path. Keep the documented no-network dry-run, `--yes` consent, unsupported Windows, and preserved runtime data unless behavior intentionally changes. `docs/cli.md:15` currently suggests downloading and running a script but does not give an independent verification command.
- A direct `curl -fsSL .../releases/latest/download/install.sh | sh` executes the downloaded script before its sidecar can be checked; the script can verify a fetched child installer or the wheel, never its own initial bytes. A manual download/verify/review/run example needs an exact pinned tag or a resolved immutable tag used for both `install.sh` and `install.sh.sha256`. Fetching both separately from `/latest/download/` leaves a release-publication race. A sidecar served by the same publisher detects mismatch/corruption but cannot establish an independent signature or defend against a compromised publisher.

## Design tension to settle before implementation

- `.trellis/tasks/09-26-release-hosted-curl-installer/design.md` calls the public asset a "stable bootstrap" that fetches another versioned installer. `/releases/latest/download/install.sh` is itself a moving versioned Release asset; there is no separate immutable stable bootstrap at that URL. Choose whether each release asset contains both selector/verified handoff and wheel-install logic, or whether a separate stable launcher exists and where it is hosted. For the proposed URL, the release asset can carry its own embedded tag; if `--version` names another release, it must download/check that release's `install.sh` before executing it, and the child must reject a supplied tag that conflicts with its embedded identity. A blindly passed selected tag is insufficient if the initial latest URL changes independently of a separate latest metadata lookup.
- Check the self-delegation boundary: if `--version` already equals the running installer's embedded tag, install directly; otherwise fetch/check the target tagged installer once and invoke it with flags so it does not recurse. For `--ref`, keep the explicit Git-source branch separate from wheel provenance and never silently treat it as a release fallback. For dry-run, retain no network or child invocation, reporting what would be selected and that checksum verification has not happened.
- `tests/test_release_validation.py:37-40` assumes static build output exists before `uv build`. If generated static assets leave Git tracking, the test must generate them in a throwaway build context or use a deterministic fixture; otherwise a clean checkout may fail while a dirty checkout passes on stale generated assets. This is separate from the installer tests but affects release artifact validation in this child.
