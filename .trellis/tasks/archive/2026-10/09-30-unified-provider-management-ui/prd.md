# 统一 provider 管理界面与快捷配置

## 目标
基于项目当前 provider、模型目录和配置流程，规划一套统一的 provider 管理界面与交互，让用户能快速新增、配置、验证和维护 provider，同时不偏离现有数据结构与系统能力。

## 已确认现状
- Provider 配置分布于静态 `models.json` catalog 与 CLI；Dashboard 当前只提供 provider 观测摘要及 routing overlay 编辑，没有 provider CRUD API。
- Provider 定义保存 `api_key_env` 等环境变量名称，不保存密钥值；模型继承 provider 连接参数。
- Provider 摘要展示近期请求证据，不是实时连通性检查。
- 删除 provider 可能影响其关联模型，CLI 对有关联模型的删除采取保护措施。
- 详细代码证据与路径见 `research/current-provider-surfaces.md`。

## 用户目标
界面结构应贴合现有系统，同时让常见 provider 配置尽可能快捷。

## 需求
- 调研当前 provider 配置的数据模型、后端接口、前端入口及已有验证/错误处理能力。
- 设计统一 provider 管理信息架构与主要交互流程，覆盖创建、编辑、启用/禁用、凭据配置和配置验证（以现有能力为准）。
- 缩短常见配置路径，优先复用现有 provider 类型、模型定义和默认值，避免要求用户重复录入可推导的信息。
- 明确配置成功、字段错误、连接验证失败、凭据缺失等状态如何反馈，并遵循凭据安全要求。
- 本任务阶段产出需求与设计规划，不直接实现产品代码。

## 验收标准
- PRD、设计和执行计划反映经代码调研确认的当前数据结构与接口边界。
- 设计说明主要页面/区域、核心交互流程、快捷配置策略及关键状态反馈。
- 设计不要求后端尚不支持的能力；缺失能力明确列为延后项或前置依赖。
- 用户审阅最终规划摘要后，再决定是否进入实现阶段。

## 范围外
- 本规划阶段不修改产品代码、不启动实现。
- 不预设新增 provider 类型、批量导入、自动探测等当前系统未确认支持的能力。

## 待确认的产品决策
- 管理界面最重要的使用入口/工作方式尚待结合现有界面调研，并在需要时向用户确认。
