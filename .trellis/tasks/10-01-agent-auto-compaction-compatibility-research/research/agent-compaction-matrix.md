本地源码状态以查询时工作树为准，不宣称为线上部署版本；未修改产品文件。

## 最小兼容契约及建议排序

1. 先支持当前可直连的 Pi、OpenCode、Aider、Cline、Roo 的明确**别名容量配置**：为一个长期会话可被路由到的目标取最小已验证输入窗口，再扣除最大输出、工具/schema、估算误差和总结余量。不能把 `context_window` 当作输入可用 tokens；客户端须使用其自己的 `contextWindow` / `maxInputTokens` / `limit.input` 设置。未知物理窗口或无容量硬约束的策略不得混入标为「安全」的别名。代价是大窗口目标不能充分利用；Aider 仅压旧对话，不保证本轮整体安全。确认部分是这些客户端有本地设置与触发代码；「覆盖多数可直连客户端」仍是待联调的目标，**不是已达成的成功率**。
2. 在 JEV 请求前决策侧增加可检验的输入预算契约与严格拒绝/选择足够窗口目标的设计评估：已知窗口不够时不得靠 policy 放宽阶梯选小模型；对真实计数及工具、非文本输入预留空间。由于客户端不会无条件读 JEV 自定义 metadata，单独增强 `/v1/models` 字段不能解决当前兼容性。若未来支持稳定别名容量公开，也应注明可用输入限制而非只报总窗口。这里是研究建议，不是改动承诺。
3. 使用请求前路由锁定、按物理模型暴露不同别名，或对 Pi 等可扩展客户端做发送前选型和容量适配，可保留大上下文收益；代价是智能路由自由度下降或需要客户端专用集成。仅在响应后识别 `X-JEV-Model` 只能调下一轮，救不了首个超限请求。应保护 streaming usage 与通用的可机读 overflow 错误，再测各客户端 retry；但错误兜底无法处理不识别的 SSE 中断、单消息过大及摘要请求也选到小模型的情形。
4. Codex 当前需 JEV Responses API（含 Codex 所需的 streaming/usage、工具及 compact 路径验证）；Claude Code 需 Anthropic Messages 协议桥接；Gemini CLI 需 Gemini 协议桥接。这三项不是自定义 base URL 即可覆盖。新协议必须单独立项并按版本验收，不能合并计算当前覆盖率。

## 可执行验证方案与主要未知项

先为每个客户端固定二进制版本/commit 与配置，准备两个真实窗口明显不同、均支持 native tool calling 的上游；同一别名分别设保守小窗口与故意过大的窗口。用无敏感数据、逐渐增长的工具结果触发临界点；捕获客户端发往网关的每轮请求 token 估算、`model`、`stream_options`，网关返回的原始 SSE（含末尾 usage）、HTTP 头及可机读错误、客户端 compact 事件/摘要请求和重试次数。做三个场景：首次本轮就超小目标窗口、使用量跨阈值后的下一轮切换到小目标、摘要请求也被路由小目标。对每个客户端分别验证压缩发生在发送前、响应后、错误后或完全不发生；重复开启/关闭 streaming usage、工具调用、单条超大消息。请求体、API key、用户代码不得进入研究日志。

- 未验证任何客户端真实接 JEV 后的 streaming usage、模型回显处理、工具调用一致性或错误恢复；OpenCode/Cline 并存运行时路径须锁定版本做实验。
- Claude Code 官方页面会演化，尚无可核对的封闭源码解释所有 usage/overflow retry 分支；官方 gateway window 修正说明也不能证明 JEV Chat Completions 兼容。
- Codex 当前主线已删除 `wire_api="chat"`，需明确计划采用的二进制版本；旧版可接入的说法仅限旧版，不能用来证明当前版。
- `context_window` 缺失时 JEV 视为无限、内置 policy 容量筛选可放宽、自定义策略可能跳过筛选；在未知目标或高估客户端容量时，没有跨客户端「一定自动 compact」保证。
