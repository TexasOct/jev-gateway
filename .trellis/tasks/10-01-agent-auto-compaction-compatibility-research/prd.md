# 调研主流 Agent 的自动上下文压缩与智能路由兼容性

## Goal

识别主流编码 Agent 如何获取模型上下文窗口、计算会话 token 使用量并触发自动 compact，评估 JEV 智能路由作为单一模型入口时能否维持各客户端的自动压缩能力，形成有证据的兼容性矩阵及后续方案建议。

## Background

- JEV 当前 `/v1/models` 返回策略名及已配置模型的 ID，不返回模型上下文窗口；网关能按请求选中不同上游模型，并在响应头 `X-JEV-Model` 标记命中模型。
- JEV 配置中的物理模型可声明 `context_window`，但不同路由目标的容量可能不同。
- 已知 Pi 的虚拟模型机制可以在请求发送前按物理模型容量检查 compact；Codex 有客户端侧模型容量及 auto-compact 配置。其他 Agent 的具体行为和兼容边界待核实。

## Requirements

1. 建立公开且可复核的 Agent 选择口径，至少覆盖 Pi、Codex，并调查多个常用可通过自定义模型或 OpenAI 兼容端点接入 JEV 的编码 Agent；对不能接入者明确标注，不把它们计入可兼容覆盖率。
2. 对每个 Agent 记录版本或来源日期、接入协议、模型容量元数据来源、token 用量来源、自动 compact 触发点、溢出恢复路径、动态路由切换后是否更新容量认知，以及事实依据链接或源码位置。
3. 对照 JEV 当前行为核对 `/v1/models`、聊天请求与响应（含流式）、`usage`、`model` 回显、错误及真实路由信息，并区分已验证、文档推断和未知项。
4. 给出可跨客户端复用的最小兼容契约、需要客户端适配的例外及不能安全覆盖的场景。评估别名保守上下文窗口、请求前路由、客户端配置和溢出兜底等选项，不预设其中任何一项足以覆盖所有 Agent。
5. 交付调研文档、兼容性矩阵及按覆盖面与实施复杂度排序的建议；保留复现步骤或验证用例建议，不在本任务中修改网关或 Agent 实现。

## Acceptance Criteria

- [ ] 每个被纳入的 Agent 都有可追溯的官方文档或源码证据；缺证据的行为标为待验证。
- [ ] 有明确的“可通过 JEV 接入”“可自动 compact”“智能路由安全性”三个不同维度，避免将支持自定义 API 等同于兼容自动压缩。
- [ ] 提供 JEV 当前接口与响应的源码定位和风险清单，说明路由到不同上下文窗口模型时何时可能过晚 compact。
- [ ] 提出覆盖多数已调查且可接入的 Agent 的建议，并列出无法保证覆盖的客户端、触发条件和所需补充实验。
- [ ] 调研结论以任务目录内的研究文件保存，不依赖本次对话；不修改产品代码。

## Scope and open decision

- 初步候选：Pi、Codex、Claude Code、Gemini CLI、OpenCode、Aider、Cline、Roo Code；以是否具备可验证的 JEV 接入方式调整矩阵，不承诺覆盖市场上所有 Agent。
- 待用户确认：本任务是只完成调研与方案，还是也要包含实际跨客户端集成实验。当前按“先调研、形成可执行验证方案，不改产品代码”执行研究阶段。
