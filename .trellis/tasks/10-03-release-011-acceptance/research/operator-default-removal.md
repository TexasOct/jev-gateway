# Behavior of removing the retired defaults block

Source-only investigation. No operator configuration, credentials, database, HTTP responses, or logs were read. No network calls or install/service mutations were performed. The candidate document and its validation belong to the parent investigation.

References below use `old/` for `/Users/texas/.local/share/uv/tools/jev-gateway/lib/python3.12/site-packages/jev_gateway/` and `current/` for the repository's `jev_gateway/`. The parent supplied the recovered installation's 0.1.0 identity; this investigation did not re-audit wheel hashes or running service health.

## Old routing behavior

- `defaults.default_model` names a configured canonical model ID; catalog validation rejects an unknown ID (`old/catalog.py:584`). It does not select a strategy.
- A request whose model field matches a registered strategy selects that strategy and passes no manual model. Other model strings retain their value as a manual model request while selecting a valid pinned session strategy, or the registry default strategy (`old/gateway.py:320`). Thus an arbitrary string such as `default` is not an implicit virtual alias unless it is a registered strategy or configured canonical model.
- Explicit canonical models take the manual branch on initial selection and when changing the current session model (`old/strategy/policy.py:80`, `:102`). The default block does not override these branches. A continuation explicitly naming the already-current model still enters continuation policy, so this is not an unconditional permanent manual pin.
- Automatic selection invokes the global default only when the requested routing label is `default` and absent from policy labels, or when that label's configured model/tag pool is empty (`old/strategy/policy.py:351`, `:383`). The global-default branch directly returns the named model before capability/context/output filtering, strategy ordering, and exclusion filtering. Consequently it can affect explicitly requested strategy IDs as well as the registry default strategy. Nonempty pools use normal policy selection, even when the global default is non-null.
- Exhausting constraints for a nonempty pool uses progressively relaxed catalog selection, not a final global-default branch (`old/strategy/policy.py:389`). The global default is not an unconditional last-resort model for every failure.
- Upstream failure counters trigger policy escalation with exclusion of the current model (`old/strategy/policy.py:307`). Selection can then encounter an empty pool and return the global default. Because that branch ignores exclusion, it can return the current model; surrounding continuation code only switches when the chosen model differs (`old/strategy/policy.py:143`, `:187`, `:251`). Pin break reasons and hysteresis determine whether escalation is attempted. This governs later routing decisions, not a guaranteed immediate retry of the failed request.
- Decision-classifier disabled/unsuccessful evaluation leaves request facts unchanged (`old/strategy/classifier.py:24`). Matrix evaluation failure uses its configured fallback; valid answers matching no rule use the first label and the policy selection rule (`old/strategy/matrix.py:46`). These labels still flow into policy selection. A matrix evidence reason of `default` does not itself mean the global default model.
- Old sessions retain a `defaulted` marker and accept a session tier of `default` even when absent from labels (`old/strategy/policy.py:69`, `:232`). Therefore preserving persisted rows does not promise identical continuation semantics after the upgrade.

## Current behavior with only defaults removed

The parent reports that its private candidate removing only defaults failed public 0.1.1 validation because a policy label resolved to a tag declared by no model. Label/tag values are intentionally withheld. Simple removal is therefore not a validated upgrade candidate.

The installed old validator omits tag-pool coverage checks unconditionally (`old/catalog.py:651`). It checks nonempty labels, valid names, explicit model references, and the prohibition on combining models with a tag, but never computes a matching tagged pool. `Catalog.validate` calls it for both catalog.policy and every strategy policy (`old/catalog.py:594`, `:613`). This is not a conditional validation bypass enabled by a non-null default_model: the same missing coverage check applies even when that field is null. The non-null field instead makes the accepted empty pool usable at runtime through `_select` and `_default_model` (`old/strategy/policy.py:351`, `:383`). Without it, such a request raises SetupIncompleteError.

Current `_validate_policy` resolves the explicit tag or the implicit strategy/label tag, collects matching profiles, and rejects a label with neither explicit models nor matching tagged profiles (`current/catalog.py:656`, `:661`). Validation covers catalog.policy and all configured strategy policies (`current/catalog.py:580`, `:599`). Consequently the runtime catalog-wide relaxation described below cannot rescue an empty pool in a normally loaded invalid catalog: validation rejects it first. An approved current-schema routing adjustment must supply valid label coverage as well as remove the retired block; this investigation has not selected or validated that adjustment.

Removing the block preserves the values of policy, strategies, default_strategy, providers, models, gateway, decision, and storage. It removes the special global-model fallback described above. It does not encode that model into a replacement policy or strategy.

- Strategy/model dispatch has the same structure (`current/gateway.py:311`). Explicit canonical model requests still resolve through catalog lookup and the manual branch (`current/decision.py:216`, `current/strategy/policy.py:77`). Explicit strategy IDs follow their own effective policies.
- `default_strategy` is an accepted top-level key, but this parser does not read its value to choose the registry default. Wrapped strategies use `strategies.default`; compact strategies choose `task_aware` (`current/catalog.py:1586`, `:1602`, `:1621`, `:1629`). Do not promise that retaining the top-level field makes it authoritative. The registry uses the parsed catalog default (`current/strategy/registry.py:146`).
- Top-level policy supplies the base policy. Strategy policies inherit/override it during parsing; catalog.policy is the effective policy of the parsed default strategy (`current/catalog.py:1781`, `:1789`, `:1801`). Policy controls labels, candidate references/tags, model ordering, session mode, pin breaks, escalation, budget, and hysteresis.
- Unknown or absent route labels use the first configured policy label. A literal route label `default` is ordinary only if actually configured (`current/strategy/policy.py:477`). Classifier and matrix fallback then use policy selection (`current/strategy/classifier.py:24`, `current/strategy/matrix.py:46`).
- For an empty label pool, selection immediately searches all catalog models. For nonempty pools, it tries the label pool and then all models at each relaxation stage: capability plus context plus output, capability plus context, capability only, then fully relaxed. Exclusion applies during this search. Final fallback excludes the current model when possible, otherwise searches the full catalog (`current/strategy/policy.py:334`). Ordering is estimated-cost/priority for cheapest_adequate, quality/priority for quality_first, or the implemented cost-quality score/priority for balanced (`current/strategy/policy.py:387`).
- An old session tier absent from current labels now takes initial selection (`current/strategy/policy.py:69`). Valid-label sessions retain continuation policy behavior. Old global-default origin is no longer used by this policy implementation.

The exact model selected after removal depends on retained labels, tags, strategy options, priorities, capabilities, request facts, and session state. This source-only investigation intentionally does not identify an operator model or predict candidate-specific routing. Removing the block can leave a formerly selected default model selected by normal policy, but does not guarantee that outcome.

## Can default upgrade finish without any configuration change?

No supported current-schema path found for starting the default operator with the unchanged document containing top-level defaults. `current/catalog.py:1735` rejects unknown top-level keys before parsing the remainder. Startup parses the overlay-merged document and, on validation failure, parses the unchanged baseline (`current/gateway.py:179`). Overlay merge deep-copies and changes routing/model fields without deleting defaults (`current/routing_overlay.py:159`). CLI validation calls the same catalog parser (`current/cli/config_ops.py:28`). Neither overlay fallback nor a null default_model makes the top-level defaults key valid.

Selecting an already-valid alternate catalog is supported by the source's models_file parameter, but changes the effective configuration and does not prove acceptance of the default operator's unchanged configuration. Replacing the baseline, using a generated document, or restoring retired-field support would change the stated constraints. No such action was taken or recommended here.

R7 therefore remains unresolved until the user explicitly approves an adjustment or the parent establishes another supported path. The recovered 0.1.0 running service establishes recovery only; it does not establish default 0.1.1 acceptance. The separately reported installed browser/backend results do not remove this operator acceptance blocker.
