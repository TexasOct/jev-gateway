## Publication gap and recommended verification gates

A release mechanism must decide how a tag is cut, verify that its version matches `pyproject.toml` and the CLI's displayed version, build in a clean environment, inspect wheel entry points/templates/static assets/license, then publish the artifact whose name the installer expects. For a GitHub Actions publisher, define trigger, permissions, artifact naming, checksum/attestation policy, and whether failed validation can leave a partial public release. An end-to-end smoke test should install the actual published URL in a throwaway home and verify `jev --version`, `jev install init`, rerun preservation, and uninstall behavior on supported platforms. Offline unit tests should stub release metadata and downloads.

Sources for GitHub behavior: [Get the latest release API](https://docs.github.com/en/rest/releases/releases), [linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases), [workflow triggers](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [GITHUB_TOKEN security](https://docs.github.com/en/actions/concepts/security/github_token). The latest-release API excludes drafts and prereleases and returns 404 when no qualifying release exists. A release is distinct from a Git tag, so tags alone will not supply a `releases/latest` install target. GitHub supports marking a published release as latest; this should be deliberate rather than assuming the numerically greatest tag always wins. Events caused by a workflow's `GITHUB_TOKEN` generally do not trigger another workflow, so a design that creates a release in one job and waits for a second `release.published` workflow may stall. This is why a single tag-triggered validation/build/publication path is worth considering, though its trigger is still a product decision.
