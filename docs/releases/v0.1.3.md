# JEV Gateway 0.1.3

This release completes the Dashboard configuration workflows across Settings,
Suppliers and Strategy workflow. Models belong to their saved supplier
connections, with one shared editor for configured models and import candidates.

## Settings and supplier connections

- Settings > Access and security owns gateway-key initialization and replacement.
  Replacement takes effect immediately; other clients must use the new key.
  The Dashboard continues to use the gateway's shared Bearer authorization.
- Supplier setup starts with a preset or connection method, then the connection
  name, address and required credentials. Multiple connections to the same brand
  keep distinct identities. Renaming a connection preserves model and strategy
  references; advanced controls retain environment and shared-reference setups.
- Saved credentials stay write-only. Empty replacement retains the saved value;
  replacement and explicit clearing remain separate actions. Vertex accepts
  service-account JSON, and Bedrock accepts access ID, secret and optional session
  token. Failed validation or writes retain the draft for retry.
- Connection tests distinguish authentication, address and network failures.
  They test supported model-list endpoints without saving configuration.
  Successful listing does not certify generation access or account balance.
- Supplier artwork uses bundled local Lobe Icons assets with pinned source and
  MIT attribution. DeepSeek uses the symbol-only whale in both color schemes.
  Loading artwork requires no runtime CDN.

## Models, discovery and metadata

- Each saved LLM supplier lists its configured models beneath its connection row.
  Edit opens the shared webpage Dialog for that exact supplier/model identity,
  including when two connections use the same upstream model ID. Discovery and
  batch import are disclosed under the owning supplier. There is no separate
  Models navigation destination.
- Discovery automatically retrieves metadata suggestions. Search, visible/batch
  selection and per-item editing support reviewing multiple candidates together.
  Existing qualified model IDs are skipped without silent overwrite.
- Metadata distinguishes reliable matches, unknown fields, conflicts, failed
  retrieval and existing models. Matching uses the serving connection and exact
  model ID or evidenced alias. An ID-only listing or similar name does not
  establish prices or capabilities. Unknown prices remain distinct from zero.
- The editor groups basic information, capabilities, limits, USD-per-million
  prices and routing attributes. It exposes automatic/manual/unknown states,
  tri-state capability drafts, source records and dates, including applicable
  cache prices and conditional price evidence. Incomplete imports require
  explicit runtime-field confirmation before becoming routable.
- Manual overrides survive refresh. Returning to automatic ownership previews
  the change. Failed or uncertain same-serving refreshes retain useful prior
  values and evidence while showing the latest uncertainty and scoped retry.
  A changed serving connection invalidates earlier automatic applicability.
- Saves validate the complete record atomically with revision protection.
  Cancel writes nothing; failed saves retain inputs. Workflow-owned tags and
  priority remain protected in the model editor. Disabled models remain editable
  but cannot be selected by normal, explicit, default or pinned routing.
- Dirty dismissal asks whether to keep editing or discard. Pending writes block
  departure. The Dialog traps keyboard focus, keeps actions reachable on narrow
  screens and returns focus to the visible model trigger or supplier fallback.

## Strategy canvas and recovery

- Blank-canvas context menus and the explicit add control create supported nodes
  at the intended zoomed/scrolled position. Node and connection actions support
  semantic deletion, with explanations for protected objects. Delete/Backspace
  inside a text field preserves graph objects.
- Undo/redo covers ordinary draft and layout edits. The selected-node inspector,
  node summaries and validation feedback identify what needs repair. Strategy
  information distinguishes policy validation/application from layout saving.
- Failed initial configuration or layout reads show an explanation and read
  retry. Unresolved layout reads block editing until saved positions are read.
  Confirmed writes followed by failed reads recover through GET only. Unknown
  write outcomes require a successful read before another mutation.
- Recovery responses and feedback stay with the operation and connection that
  admitted them. Retired responses after navigation or reconnection cannot
  replace current drafts, disconnect a new session or clear a newer busy state.

## Compatibility and verification scope

Existing catalogs retain omission defaults for optional model fields. Supplier
and model identities, credential references and strategy references remain
stable. Baseline model/supplier transactions, routing overlays and canvas layout
continue to use separate persistence boundaries with existing authorization and
rollback protections. No destructive catalog migration is required. An unchanged
finite legacy quality value can survive an unrelated edit; new or changed quality
must be within `0..1`.

Gateway and supplier secrets remain in browser memory only. Locale remains the
only persisted browser preference. Installed wheels include the Dashboard and
local artwork; source packaging must build frontend assets first. Python 3.12+
remains required. Dependency resolution is unchanged by the version bump.

Independent current-source acceptance passed all 655 browser cases (646 preview
and 9 cloud), with zero skips and retries and both real synthetic credential
modes. Backend persistence and rollback evidence has its separately recorded
scope; synthetic checks do not certify external generation or operator upgrades.

At preparation, committed-source release build validation, installed 0.1.3
verification, the same-wheel Ubuntu/macOS CI checks, stable publication and public
installer/asset acceptance remain pending. This document does not claim those
release steps have passed. See [the release procedure](../releasing.md) and
[Dashboard configuration workflows](../admin-experience.md) for operational and
compatibility details.
