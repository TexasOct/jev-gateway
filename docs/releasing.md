# Publishing a GitHub Release

The public curl bootstrap stays at raw `main`. A published Release supplies the wheel and matching SHA256 asset. No first public Release is created by adding this workflow.

1. Protect tags matching `v*` in repository rules so only authorized maintainers can publish. The tag-push workflow uses `GITHUB_TOKEN` with `contents: write` and does not rely on a second release event.
2. Update `project.version` in `pyproject.toml` using `X.Y.Z` for stable or `X.Y.ZrcN` (also `aN`/`bN`) for prereleases. Review the changes, run `uv run pytest -q`, `uvx pyright`, `scripts/build-frontend.sh --check`, `uv build`, and `python3 scripts/validate-release.py vX.Y.Z dist` (substitute the actual version). Validation inspects metadata, CLI entry points, packaged templates, dashboard and license, and writes the wheel's `.sha256` sidecar. The workflow also runs the Python tests, Pyright, and dashboard freshness check before publication.
3. After the release commit is on the intended branch, create and push `v<project.version>` from that commit. The single tag-triggered workflow checks out the tag, builds in isolation, validates and publishes both assets with generated release notes. Stable versions are marked latest; prereleases are explicitly marked prerelease and cannot become the default installer target. Do not upload artifacts from a dirty local `dist/`.
4. Once publication succeeds, test a throwaway-home installation with `--version X.Y.Z` and confirm `jev --version`, `jev doctor`, repeat-install preservation and normal uninstall. Until a published stable Release exists, the default installer exits with an actionable error. To roll back, rerun the installer with `--version` pointing to a previously published Release; runtime data remains in place.

A missing or malformed asset or mismatched digest stops installation before replacing the CLI. A checksum tied to the same Release detects transfer errors and asset inconsistencies; it does not provide an independent signature against a compromised Release publisher. The raw-main bootstrap can change over time, so review it before executing it. If publication fails after GitHub creates a draft Release, inspect or remove that draft before retrying; the workflow refuses an existing draft or published Release for the same tag.
